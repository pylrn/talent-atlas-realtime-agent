The project in one minute

Turn a hiring request into an evidence-backed shortlist.

Talent Atlas is a hybrid RAG search system. A recruiter describes the person they need in ordinary language; the system searches the meaning inside resumes, protects exact requirements such as skills and location, and returns one ranked list with the source evidence behind every match.

The AI copilot makes that search conversational, but it does not invent candidates or decide scores. It turns the recruiter’s request into a validated search, calls the same deterministic engine, and explains only what the returned evidence supports.

Before the implementation

What “hybrid RAG” means here

RAG stands for retrieval-augmented generation: find relevant information first, then let an AI answer using that information. Talent Atlas makes the retrieval stage hybrid because no single search method is reliable enough for resumes.

01 / Retrieve

Search meaning and exact facts

Vector search finds similar ideas even when the wording differs. Keyword, skill and SQL search protect names, technologies, locations and hard requirements.

02 / Fuse

Combine independent evidence

Each search method produces a different kind of score. Reciprocal Rank Fusion compares their positions instead, rewarding candidates supported by several methods.

03 / Rerank

Give the best matches a second review

A cross-encoder reads the request and the strongest resume passages together. It is slower, so it judges only the small pool retrieved in the earlier stages.

04 / Ground

Answer from the retrieved source

The API returns candidate facts, matching resume text and score details. The copilot uses that evidence to explain results instead of relying on what the LLM remembers.

In one sentence: hybrid search reduces what the system misses, reranking improves what reaches the top, and grounding keeps the AI explanation tied to the underlying resume evidence.

01 / How it works

How the hybrid RAG pipeline works

The search engine is the center. The API makes it configurable, the agent turns conversation into typed calls, and the learning layer supplies guarded preferences and outcome signals. The pipeline separates recall from judgment: retrieve a broad pool, combine independent evidence, then spend more computation only on the strongest candidates.

SearchTurn the request into explicit requirements.

RetrieveFind meaning, exact text, and exact skills in parallel.

RankFuse agreement, score candidate evidence, and remove near-duplicates.

ExplainReturn the source text and score components with every person.

Unlike a basic document chatbot, the retrieval result here is already a structured, ranked candidate response. Generation happens afterward: the copilot consumes those records and their source evidence to answer or explain.

The system’s stable spine

POST/search

One endpoint, twenty deliberate steps

The Search UI, recruiting agent and benchmark scripts all use the same typed contract. FastAPI first validates the JSON, combines the selected mode with any safe overrides, and hands one request to the search engine. The engine then runs the sequence below and returns candidates, evidence, ranking details, timings and retrieval diagnostics in one response.

Not every request pays for every stage. A name lookup or filter-only request exits early; fast mode skips the cross-encoder; no-llm uses the deterministic planner; and every optional stage has a defined fallback.

01–05

Understand safely

  1. Detect the route

    Recognize a normal query, pasted job description, name lookup or filter-only request.

  2. Sanitize the input

    Bound its length, remove control characters and isolate user text before prompting.

  3. Check the caches

    Reuse matching planner, HyDE and embedding work when model and prompt versions agree.

  4. Plan the request

    Use the LLM for nuanced language or the deterministic fallback when disabled or unavailable.

  5. Validate the plan

    Drop unsupported fields, forbidden criteria and skills that were not grounded in the request.

06–10

Compile the search

  1. Normalize aliases

    Map terms such as “JS,” “K8s” and “Bengaluru” to the values stored in PostgreSQL.

  2. Apply the confidence gate

    Ask a focused question when the request is too ambiguous to search responsibly.

  3. Route the intent

    Send lookups and filter-only requests down cheaper paths; reserve retrieval for candidate search.

  4. Weight search targets

    Prefer requested sources such as resumes or projects without deleting useful evidence elsewhere.

  5. Build the SQL filter

    Turn mandatory status, location, salary, experience and skill rules into the eligible pool.

11–15

Retrieve and combine

  1. Run dense retrieval

    Embed the semantic query or HyDE profile and search resume chunks through pgvector HNSW.

  2. Run keyword retrieval

    Protect rare tools and exact phrases with PostgreSQL full-text search or optional BM25.

  3. Run exact-skill retrieval

    Score canonical candidate skills directly instead of hoping they appear prominently in prose.

  4. Fuse with RRF

    Combine branch positions with Σ 1 / (60 + rank), rewarding agreement across methods.

  5. Group by candidate

    Hydrate the strongest chunks, collapse duplicates and retain supporting passages as evidence.

16–20

Judge, explain and learn

  1. Guard empty results

    Make at most one bounded relaxation, record it, and rerun rather than silently broadening forever.

  2. Rerank the prefix

    Optionally let the cross-encoder read each query and evidence pair for the strongest small pool.

  3. Compute the feature score

    Combine retrieval, skills, preferences, experience, recency and completeness with tested weights.

  4. Apply MMR and explain

    Balance relevance with duplicate reduction, then attach checks, score components and best evidence.

  5. Return and observe

    Serialize SearchResponse, timings and trace metadata; log impressions and history asynchronously.

The important boundary: the LLM may interpret language, but PostgreSQL decides eligibility, the retrieval and ranking stages decide order, and the returned source text is what the UI and agent are allowed to explain.

02 / The first search

I built the search engine before I built the copilot

The first useful version was intentionally plain: one FastAPI endpoint, PostgreSQL, pgvector, a small admin interface, and enough synthetic candidates to inspect every join and score.

The project began as a scalable rewrite of an earlier smart-search prototype. A recruiter query had to reach two kinds of truth at once: structured candidate facts such as status, location, salary and years of experience, and unstructured evidence inside resumes, notes and uploads. Keeping both in PostgreSQL meant filters, full-text search, vector distance and source joins could share one transactional model.

The data model became the first important boundary. A candidate holds operational facts. A document preserves the source and its provenance. A chunk is the searchable unit with text, a full-text representation and an embedding. That separation made it possible to return a person once while still showing the exact resume fragments that caused the match.

The hard part was not finding a large CSV

One hundred generated profiles proved persistence and request mechanics, but they were useless as a serious relevance test. I then moved to a real public Kaggle recruitment dataset and inspected its rows against the application schema. Public does not automatically mean usable: a large file can still be a poor fit if it lacks resume text, role context or evidence that can support a result.

The first real import transformed 5,000 Kaggle recruitment rows into candidates, resume documents and evaluation cases while preserving the source names, roles, resumes and job descriptions. Only missing demonstration fields such as location and salary were generated deterministically, and emails were replaced with placeholders. Later resume-first corpora required deduplication, template cleanup, role normalization, canonical skills, stable source IDs and caps on overrepresented jobs. The local corpus eventually reached 30,767 candidates, 28,610 documents and 65,211 chunks.

03 / The retrieval pipeline

Semantic similarity was a useful scout, not a final judge

Dense retrieval found related language, but it could miss exact skills, accept a conceptually similar resume that failed a hard constraint, or return several chunks from the same person.

I used all-MiniLM-L6-v2 as the local baseline because it was designed for sentence and short-paragraph similarity, was trained on more than a billion sentence pairs, produced compact 384-dimensional vectors, and ran locally at zero request cost. That was a practical match for searching resume chunks. It was not selected because “smaller is always more accurate”; the repository keeps adapters for larger local and hosted models because changing the embedding model is a corpus migration, not a dropdown-only change.

Dense search therefore became one of three parallel branches. PostgreSQL full-text search protects exact phrases, acronyms and unusual terms. The skill branch searches normalized candidate facts. Reciprocal Rank Fusion then combines positions instead of incompatible raw scores:

RRF(d) = Σ 1 / (60 + rankbranch(d))

The constant 60 smooths the advantage of a single first-place result. A candidate found near the top by dense, keyword and skill retrieval receives more evidence than one found by only one branch. Results are then grouped by candidate ID so repeated chunks become supporting evidence instead of repeated people.

Why the cross-encoder stayed optional

The local reranker uses cross-encoder/ms-marco-MiniLM-L-6-v2. Its training task is passage ranking: it reads the query and candidate evidence together and emits one relevance score. That makes it a much closer fit for second-stage ranking than a bi-encoder, which must encode each side independently so documents can be indexed in advance. The cost is that every query-document pair must run through the model at request time, so only a retrieved prefix is reranked.

Architectural fit still did not guarantee better project results. On the recorded 80-query evaluation, enabling reranking reduced Top-1 from 35% to 28.75% and raised median latency from roughly 60 ms to 244 ms. I kept the stage toggleable and let the feature ranker redistribute its weights when it is absent. That negative result mattered more than the model’s reputation.

See the final score and diversity formulas

With the cross-encoder enabled, the current score weights cross-encoder relevance at 45%, retrieval at 20%, exact skills at 12%, soft preferences at 10%, experience fit at 5%, skill recency at 3%, completeness at 2%, and confirmed personalization at 3%.

feature_score = 100 × Σ(signal_i × normalized_weight_i)

MMR(candidate) =
  0.7 × relevance
  − 0.3 × max_similarity_to_already_selected

Without cross-encoder scores, retrieval and deterministic candidate facts receive the missing weight. MMR runs last so diversity can remove near-duplicates without rescuing irrelevant candidates.

04 / JSON as the contract

One JSON contract connected the endpoint, tools and UI

Once the basic pipeline worked, I stopped treating the request as only a sentence. JSON became the stable language for configuring search directly and for passing validated arguments and results through the chatbot’s predefined tools.

Direct endpoint calls: POST /search accepts free text or a job description alongside structured filters, soft preferences, weights, mode, result count, keyword policy and pipeline toggles. Pydantic validates the body, and the search service compiles it into a canonical specification containing must constraints, should preferences, lexical terms and a semantic query. This JSON configures known pipeline behavior; it is not executable code.

Named modes establish sensible combinations of these values. Explicit request fields take priority where appropriate, so experiments remain reproducible without forcing normal UI users to understand every internal stage.

Chatbot tool calls: PydanticAI turns a fixed set of registered Python functions into schemas the model can see. The model can select run_search, modify_and_search, view_current_results, list_skills, keyword_search, get_candidate_details, update_shortlist and other predefined operations, then provide JSON arguments that match the chosen function. It cannot invent a function or bypass the validation layer.

Each function delegates to deterministic do_* helpers. Search functions call the shared engine; inspection functions query candidate evidence; workflow functions update explicit session state. Their JSON return values carry results, diagnostics, scores and evidence. The chat endpoint observes those tool events and translates them into server-sent status updates and candidate cards before the model writes a grounded summary.

This is also where flexibility became safe. Search modes merge base configuration, a named preset, provider settings and request overrides without changing the result shape. The planner prompt extracts only grounded requirements and separates mandatory from preferred criteria, but code still normalizes aliases, rejects unsupported fields and enforces database policy.

05 / Making it agent-callable

The agent learned the endpoint’s language instead of replacing it

By the time the recruiting copilot arrived, the difficult search logic already had a stable JSON boundary and a set of deterministic helpers. The agent became a router across those capabilities, not a second ranking implementation.

PydanticAI provides typed dependencies, generated tool schemas, message history and node-level streaming. Search tools include run_search and modify_and_search; inspection tools include view_current_results, list_skills, keyword_search and batched candidate detail lookup; workflow tools include shortlist, working-spec, saved-search and export operations. Every one is a predefined Python function with validated arguments and a JSON result.

The system prompt is an operating contract, not a personality paragraph. It maps recruiter intents to the appropriate registered tool, explains which fields belong in hard filters versus soft preferences, and requires candidate claims to come from returned evidence. Provider SDKs are still used directly for planner and embedding adapters; PydanticAI owns the conversational tool loop, not every model call.

Public-safe excerpt from the agent system prompt

The instructions narrow the model’s job

The prompt first explains the platform and its ranking fields. It then injects the current query, active filters, result count, confirmed recruiter facts and unconfirmed observations. Candidate profiles are deliberately not placed in the prompt; the agent must fetch evidence through a tool when it needs it.

Specific requests run immediately. Broad requests become a compact requirements draft with one or two focused questions. Explicit must-haves go into filters; optional or inferred preferences go into should. When the agent has already built the JSON itself, it chooses no-llm so the backend does not pay another model to reinterpret it.

Finally, the prompt defines recovery rules: inspect the returned diagnostics, relax the smallest constraint first, explain rankings from best_evidence and score data, never invent a candidate, and ask before saving a lasting preference. 

You are an expert AI recruiting copilot.

SPECIFIC request → act immediately.
BROAD request → draft requirements,
then ask 1–2 focused questions.

Only explicit must-haves belong in filters.
Optional criteria belong in should.
Prefer no-llm after structuring the request.

Read best_evidence before explaining a rank.
Never invent candidates or numbers.

The agent decides

Whether to clarify, which tool to call, how to structure the brief, and how to explain returned evidence.

Deterministic

The chat endpoint observes the PydanticAI run and translates model and tool nodes into server-sent events. The UI can therefore show “searching,” tool arguments, result cards and the final answer without putting display concerns inside the tools. Langfuse traces the request, model generations, tool calls and search spans as one nested path, which made slow model calls and database waits distinguishable.

Following one request

Langfuse turned “the agent feels slow” into a path I could inspect

At first I only had a few endpoint timers. They could tell me that a request took a long time, but not whether the delay came from the model thinking, a tool call, waiting for a database connection, one retrieval branch, or the cross-encoder. I changed that to one root trace for each recruiter turn. Under it, the model generations, tool calls and search operation become nested observations with their own inputs, outputs and timings.

The first image is the actual order reconstructed from a recorded Langfuse trace. The agent checked canonical skills twice, then called the candidate-search tool. That search occupied most of the turn. The second image opens that tool call: count, dense, exact-skill and keyword retrieval start together; RRF waits for the slowest branch; candidate rows are hydrated; then the cross-encoder reranks the final window. This showed that the apparent “agent delay” was mostly retrieval and database waiting, with another measurable cost in reranking.

That separation matters because each problem has a different fix. A slow generation suggests a smaller model or tighter prompt. A pool wait suggests connection or concurrency work. A weak keyword branch suggests query or index work. A slow reranker can be warmed, applied to fewer candidates, or disabled in a faster mode. The trace records the decision path without changing the deterministic search result, and production tracing can sample requests and redact prompt or candidate content.

These are public-safe crops from a project trace analysis. The private trace identifier and candidate payloads are intentionally omitted; timings describe that recorded run, not a universal latency guarantee.

06 / Learning and flexibility

Memory could help only after it stopped being invisible

A recruiting assistant should remember useful context, but clicks are not consent and repeated behavior is not automatically a hiring rule.

The memory design separates recruiter-declared facts from machine observations. Facts are editable and may softly influence planning. Observations keep confidence, evidence and expiry, but cannot affect ranking until they are confirmed. Even active personalization is a bounded score component, not a hidden SQL filter, and it is disabled by default in the current configuration.

This same principle shaped the product UI. Search sessions restore the working spec and results; tool calls stay visible; candidate cards preserve supporting evidence; shortlist and outcome actions carry reasons; uploads become documents rather than pasted prompt context. The interface can learn from work because the underlying state is explicit.

07 / What held up

The architecture improved when each intelligent part had a smaller job

01

Data quality beat model novelty

A stronger model could not repair absent evidence, duplicate resumes or invented schema fields.

02

JSON made intelligence composable

The same validated contract serves the UI, benchmarks, direct API clients and agent tools.

03

Models needed task-shaped roles

A bi-encoder retrieves cheaply; a cross-encoder judges a small prefix; an LLM interprets language and chooses actions.

04

Extra sophistication needed evidence

The reranker stayed optional because the measured project result was worse, despite a convincing theoretical fit.

05

Observability came before optimization

Nested traces separated planner, queue, SQL, retrieval, ranking and tool time before performance work began.

06

Learning needed a permission boundary

Observed behavior remains evidence until a recruiter confirms it as a preference.

07

Scale was tested; production fit is the next proof

The system was benchmarked and exercised with concurrent HTTP batches up to 500 requests, exposing its database-pool limits. The remaining validation is against a real company production dataset, recruiter-labelled relevance and representative live traffic. The current corpus is transformed from real Kaggle recruitment data, with generated fields kept explicitly synthetic.

The current system is hybrid by responsibility.

PostgreSQL owns facts and retrieval. Deterministic Python owns ranking and state. Small specialized models own representations and pairwise relevance. The agent owns language, tool choice and grounded explanation. That separation is what makes Talent Atlas a hybrid RAG system rather than a chatbot wrapped around vector search.
